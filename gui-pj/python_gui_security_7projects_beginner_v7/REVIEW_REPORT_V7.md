## 2. 見つけた主な問題点と実際の修正

### 問題A：全行解説が同じ記号の再出現を省いていた

v6ではたとえば `summary = tk.StringVar(value="...")` という1行に `=` が2個あっても、部品別の説明に代入用の`=`しか現れないことがあった。`set(...)` の複数回出現も欠けた。元のソースが正しいままでも、**説明表がコードの構成要素を網羅していなかった**。

対応：Python標準ライブラリの`tokenize`から7ソースすべてのトークンを取得し、空行以外の696行について**全6,504要素を出現順・重複込み**で説明し直した。`tests/test_v7_token_integrity.py`は省略・順序違い・コード全文との不一致を検出する。

### 問題B：同じ構文に異なる意味があるのに、固定した説明を流用していた

- `def summarize(events, filter_text="")` の `=` は仮引数のデフォルト値。代入文ではない。
- `tk.StringVar(value="...")` の `=` は呼び出しのキーワード引数。左側の変数への代入とは異なる。
- `raise ValueError(...) from error` は例外の原因をつなぐ構文。`from pathlib import Path` と異なる。
- `except ValueError as error` / `with ... as handle` / `import ... as tk` も、それぞれ例外の受け取り、リソース名、別名を意味する。
- `set(reader.fieldnames)` は組込み集合生成、`summary.set(...)` はGUI状態の更新。
- `before.keys() | after.keys()` はキー集合の和集合、`os.O_RDONLY | O_NOFOLLOW` はビットフラグ結合。
- `if ...:` の `:` は字下げブロック、`{key: value}` の `:` は辞書の区切り、`text[1:]` はスライス区切り。
- `or` / `and` は短絡評価し得るため、右側の演算が常に実行されるとは限らない。

対応：各行の括弧・構文の位置を考慮した記号説明へ修正。第4章にも紛らわしい構文の対照表を新設。

### 問題C：変数名の説明が抽象的で初学者向けとして不足していた

`reader`、`item`、`row`、`fieldnames`、`output`、`model`、`command`、`textvariable`などを「変数・関数などの名前」とするだけでは、何を保持しどこで使うか不明瞭だった。

対応：**約1,000箇所**の説明を、CSVの現在行、GUI部品、検査対象のドメイン、例外オブジェクト、仮想時計など、コード上の役割が分かる文章へ書き換えた。

### 問題D：読むだけでは値の変化が分かりづらかった

対応：7作品それぞれに6件、計42件の「実測精読」表を設置。実際のコードの行番号、何を入力し、どこで検証・整形し、GUIにどのように出るか、何を断定できないかをまとめた。

## 5. 各作品で説明した、保証できないこと

- 認証ログ：日時文字列の正当性や、複数の失敗が攻撃かどうかは判断しない。
- HTTPヘッダー：ヘッダーがあってもCSPなどの設定が有効か、ブラウザーがどう扱うかまでは判断しない。
- ファイアウォール：単独の行を評価するだけで、ルール順序・経路・別機器の設定などを扱わない。
- IOC：IOCの完全一致は調査の起点であり、実際の感染や侵害の証明ではない。
- ハッシュ比較：同時変更を完全に検出できず、原子的なスナップショットを作らない。復旧・改ざん防止機能ではない。
- メールヘッダー：貼り付けたAuthentication-Resultsは真正性を検証できず、FromとReply-Toの違いだけで詐欺は断定できない。
- 試行制限：実時刻・実アカウント・認証サーバー・ネットワーク・分散試行を使わないシミュレーション。
