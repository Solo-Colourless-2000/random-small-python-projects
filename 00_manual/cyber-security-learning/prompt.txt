# Pythonミニプロジェクト教材 作成指示

新しいPythonの小規模プロジェクトを10個考案し、完全な初学者でも自分で入力・実行して理解できる、非常に詳細な日本語HTMLマニュアルと完成ソースコードを作成してください。

マニュアル、完成コード、必要なサンプル、テスト、題材台帳、検証記録をZIPにまとめ、このタスクの結果にクリック可能なダウンロードリンクを提示してください。計画や題材一覧だけで終了せず、動作する実物と確認済みの教材を納品してください。

完成後、配布前に教材全体を10周以上、異なる観点から再点検してください。回数を形式的に満たすのではなく、問題を発見し、修正し、影響する範囲を再検証します。実施していない検証や確認回数を実施済みと記録してはいけません。

優先する品質は、内容の正確性、手順の再現性、初学者が処理を追える説明、1日で完成できる基本実習の分量です。説明を増やすために実装自体を複雑にせず、詳しい復習は折り畳みなどで補ってください。

## 1. 題材と分量

- 毎回、実質的に新しいPythonプロジェクトを10個作ります。
- 1作品の基本実習は18〜30分、10作品の合計は約250分を目安にします。準備・休憩・確認を含め5〜6時間程度で終えられる構成を目指します。所要時間は保証ではなく、入力速度や習熟度で変わる目安です。
- 基本実習には、その作品に必要な説明を読む、コードを入力する、保存する、基本例を実行する、結果を照合する時間を含めます。完成版を起動するだけの時間を「制作時間」として数えません。
- 全解説の通読、追加問題、応用実験は任意の復習とし、その時間を基本実習と区別します。Pythonやvimの新規導入に必要な時間も別記します。
- 10作品はそれぞれ独立して完成・実行できる構成にします。前の作品の完成や生成物を次の必須条件にしません。
- Python標準ライブラリを中心にし、原則としてサードパーティーライブラリ、外部アカウント、APIキー、外部サーバーを必要としない題材を選びます。
- Linuxで役立つ道具、文章・データ・学習・計算・小さな遊びなど、用途と学習テーマに変化を付けます。ネットワークやセキュリティの題材も適度に取り入れて構いませんが、基本実習をオフラインのサンプルで再現できるようにします。
- 1作品へ多数の機能を詰め込みません。基本実習の機能と、未実装の追加案を明確に分けます。行数を減らすために難しい1行へ処理を圧縮しません。
- 基礎構文を繰り返し使うことは認めますが、題名、入力値、単位、表示文言だけを変えた既出作品は新規題材として扱いません。

## 2. 日本語と英語の使用ルール

マニュアルの説明文は日本語、学習用コードは英語・ASCII文字のみとします。

以下に日本語を含めないでください。

- Pythonのソースコード、コメント、docstring、識別子、文字列リテラル。
- 入力プロンプト、プログラム自身が表示する案内・結果・エラーメッセージ。
- 工程別コード、基礎例、付録の完成コード、練習問題の解答コード。
- テストコード、教材として用意するテストデータとサンプル入力。
- シェルスクリプト、実行コマンド、コード欄に掲載する出力例。

日本語の解説はコード欄の外に置きます。日本語をUnicodeエスケープで隠して、実行すると日本語を出すような回避もしません。教材に用意するファイル名・パスもASCIIにそろえます。HTMLの日本語本文、目次、操作ラベル、README、点検記録、題材台帳の日本語はこの制限の対象外です。

Pythonコードの例：

```python
def main():
    count = 5
    print(f"Count: {count}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

コード、工程の抜粋、付録、テスト、サンプル、コマンドについてASCII検査を実施します。日本語の本文までASCIIへ変換しないでください。

英語の表示は本文で意味を説明します。利用者自身の入力やOS由来のエラー詳細には、環境によってASCII以外の文字が含まれ得ます。プログラムの英語メッセージと外部データを区別し、どの環境でも出力が必ずASCIIになるとは説明しません。

## 3. 開発環境とvim

- OSの操作手順はLinuxを基本とし、Arch Linux / Linux Mint / Kali Linuxなどを想定します。
- Python 3.10以上を基準とし、実行コマンドは原則としてpython3に統一します。
- エディターはvimを使用します。nanoを使う手順は掲載しません。利用者がNeovimを使用する場合はvimをnvimに置き換えられる旨を補足して構いません。
- 実際に検証したOS・Pythonバージョンを明記し、未検証の環境まで動作確認済みとしません。
- 新しいPythonの構文やAPIを使う場合は対応バージョンを調べます。3.11以降の機能などを、説明せず3.10で使えるものとして採用しません。
- 標準ライブラリだけならpipや仮想環境を基本実習の必須作業にしません。

準備手順には次を含めます。

```bash
python3 --version
pwd
ls
mkdir -p practice
vim practice/01_project_name.py
```

vimの初回説明では操作を省略しません。

1. vimとファイル名で開く。
2. iを押して挿入モードへ入る。
3. コードを入力する。
4. Escでノーマルモードへ戻る。
5. :wqと入力し、Enterで保存・終了する。
6. ターミナルへ戻り、python3 practice/01_project_name.pyで実行する。

:wqはPythonコードでもシェルコマンドでもなく、vimのノーマルモードから実行する操作であることを明記します。保存のみの:w、変更を捨てる:q!、取り消しのu、末尾から再開するG → oも必要に応じて補足します。貼り付け時に字下げが増える場合の対処も示します。

4スペースの字下げ、タブとスペースを混ぜないこと、UTF-8のプレーンテキスト、拡張子.py、.py.txtの取り違えを説明します。コマンド実行時の現在地と相対パスの基準を明示します。$など説明用のプロンプト記号は、コピーするコマンドへ含めません。

## 6. Pythonの正確性に関する重点事項

以下は、その日のコードで実際に使う項目を重点的に確認・解説します。全作品へすべての高度な概念を詰め込む必要はありません。

### 名前・型・比較

- Pythonの名前はオブジェクトへ結びつくものであり、代入が常に独立したコピーを作るとは説明しません。
- str、int、float、bool、list、tuple、dictなど、その作品に登場する型を区別します。
- =は代入、==は等価比較、isは同一オブジェクトかの判定です。数値・文字列の等価比較にisを使いません。
- 真偽値、空文字・空リストなどの扱い、and・or・notの意味を正しく説明します。and・orが常にboolそのものを返すという一般化はしません。
- ミュータブルな値の共有、浅いコピー、デフォルト引数などを使う場合は、その挙動を確認します。説明に見合わない複雑な使い方は避けます。

### 数値と演算

- 文字列の連結と数値の加算、/と//、%、演算の優先順位を区別します。
- intは固定桁数のC整数と同じ意味のオーバーフローを起こすものとして説明しません。一方、入力長・計算量・メモリを無制限に使わせる設計もしません。
- floatは多くの小数を近似で表すこと、表示の丸めと計算値が異なること、必要な場合のmath.isfiniteによるnan・無限大の検査を説明します。
- //を単に「小数部分を取り去る」と一般化せず、負数を扱う場合も確認します。
- 0除算、範囲外、無効な単位、数値変換失敗を計算前に扱います。金額など整数単位で表せる題材は、必要以上にfloatを使いません。

### 文字列とコレクション

- lenが数えるものを明示し、UTF-8のバイト数、Pythonの文字列の長さ、表示幅を同じものとして扱いません。
- 添字は0から、スライスとrangeの終点は原則として含まないことを具体例で示します。
- strip、split、join、lower、casefoldなどが何を変更・保持・生成するかを説明します。
- 空文字、空のデータ、先頭・末尾の空白、大小文字、改行の扱いを仕様として決めます。
- 内包表記、ジェネレーター式、アンパック、条件式は、採用するなら普通のforやifに読み替える説明を付けます。
- リストを変更する操作と新しい値を返す操作を区別し、繰り返し中の要素削除などで意図しない挙動を起こさないか確認します。

### 関数・制御・例外

- defは定義、呼び出しで実行されることを説明します。
- return、break、continueが終了・再開する範囲を区別します。
- inputとsys.argvは基本的に文字列を受け取ることを前提に、変換と値の検査を分けます。
- 対話型では空入力、EOF、必要に応じてCtrl+Cを扱います。再入力にするか、説明して終了するかを統一します。
- exceptは想定する例外を対象にし、理由なくexcept:ですべてを隠しません。エラーを握りつぶして成功扱いしません。
- if __name__ == "__main__":と、mainの戻り値をSystemExitで渡す仕組みを説明します。成功0、入力の問題2、I/Oや中断1など、採用した規約を明示します。クイズの不正解とプログラムの失敗を混同しません。
- 学習用入力を実行するeval・execや、不要なシェル経由の実行を安易に使いません。

### パス・ファイル・日付・乱数など

- 現在地とスクリプト配置場所を区別します。Pathは作るだけではファイルを作成しないことも説明します。
- ファイルは適切な文字コードを指定し、原則としてwithで閉じます。ファイル不在、権限、文字コードなどの想定する失敗を扱います。
- 出力先と既存ファイルをどう扱うかを明記します。新規作成が目的ならxモードなどで不用意な上書きを防ぎます。
- ファイルのクローズ、排他的作成、原子的な保存は別の性質です。withやxだけで障害時の完全な巻き戻しを保証するとは説明しません。
- サンプルを使って検証し、利用者の実データを変更することを必須実習にしません。
- 日付差、基準日、今日、時刻、タイムゾーン、日またぎを区別し、固定サンプルは後日に読んでも再現できるようにします。
- 乱数を使う場合は再現可能な検証方法を用意します。通常のrandomと秘密情報向けのsecretsの用途を混同しません。
- URL分解やIP判定などの形式検査を、実際の到達性や安全性の証明として説明しません。

## 12. 動作・整合性の検証

### 全10作品の実行

構文を確認しただけで動作検証済みとはしません。全10作品を実際に実行し、正常例、代表的な入力ミス、最小・最大・境界値、空入力、必要に応じてEOF・中断、ファイルの読み書きと上書き防止を確認します。

標準ライブラリのunittest、subprocess、tempfileなどを使い、他人のデータや既存成果物を変えない場所で検証します。終了ステータス、stdout、必要なstderr、生成ファイルの内容を確認します。

教材へ掲載する実行例は実測結果から作成します。出力例を想像で書きません。対話の入力エコー、乱数、日付、OS依存の文言など、変動する部分は固定サンプルや検査方法を工夫し、変わる範囲を説明します。

テストは実装と同じ計算を書き直して合うかを見るだけでなく、手計算できる期待値、合計の不変条件、独立した簡単なモデル、境界の前後などを使います。テスト件数やカバレッジの見栄えを目的にしません。

標準的な実行例：

```bash
python3 -m unittest discover -s tests -v
```

必要ならpy_compileなどで構文も検査します。ただし、構文検査だけで標準ライブラリAPIのバージョン互換性まで証明したとは扱いません。実測した検証環境と、未実機確認の対応範囲を分けて記録します。

1. HTMLの工程を順に連結したコード。
